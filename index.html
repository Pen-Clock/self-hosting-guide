Host your app yourself, without Vercel

A step-by-step guide to putting a frontend and a backend on the internet yourself: on a plain Linux server, on AWS, or on Cloudflare.

Platforms like Vercel, Netlify and Render take care of a lot of jobs for you without showing you. When you host it yourself, each of those jobs becomes something you do:

ℹ️ How to use this guide

Do Part 1 first, even if you plan to use AWS or Cloudflare later. It shows you what's actually going on, and the cloud services are mostly managed versions of the same pieces. Tick "Mark done" as you finish each step. Your progress is saved in your browser.

How it all fits together

This is what you'll build in Part 1. Everything runs on one server, and one program (the reverse proxy) sits at the front and sends each request to the right place.

Some ideas to keep in mind:

  • The frontend is just files. After npm run build, a React, Vue, Svelte or Vite app becomes HTML, CSS and JS files. Any web server can send those to the browser.
  • The backend is a program that keeps running. Something has to start it, restart it when it crashes, and start it again when the server reboots. systemd does that.
  • Only the reverse proxy faces the internet. Your backend and database only listen on 127.0.0.1 (localhost), so nobody can reach them directly.
  • Frontend and API share one domain. The browser calls /api/... on the same origin, so you don't have to deal with CORS.

What you need

  • A working app: a frontend (React/Vue/etc.) and a backend (Express, Fastify, FastAPI, Django, Go…) in a Git repo.
  • A domain name (~$10/year from Cloudflare Registrar, Namecheap, Porkbun…).
  • A terminal on your computer (macOS/Linux terminal, or Windows Terminal with WSL or PowerShell).
  • About $5/month for a server.
  • Basic comfort with the command line (cd, ls, editing a file with nano).

Core concepts (read this once)

Most self-hosting problems come from not knowing which piece is broken. Ten minutes on how a request travels will save you hours of debugging later.

What happens when someone visits https://myapp.com

  1. DNS lookup: the browser asks "what IP is myapp.com?" A DNS resolver looks up your domain's A record and answers 203.0.113.10. If this is wrong, nothing else matters.
  2. TCP connection: the browser opens a connection to 203.0.113.10 on port 443. Your cloud firewall and ufw both have to allow it, or the request times out.
  3. TLS handshake: the server shows a certificate proving it really is myapp.com, and they agree on encryption keys. If the certificate is missing or for the wrong domain, you get a "Your connection is not private" warning.
  4. HTTP request: the browser sends GET /dashboard with headers such as Host: myapp.com.
  5. Reverse proxy decides: Caddy looks at the path. /api/... gets forwarded to 127.0.0.1:3000; anything else gets a file from /var/www/myapp.
  6. Backend runs your code: it may query Postgres on localhost:5432, then sends back JSON. If the backend is down, Caddy returns 502 Bad Gateway.
  7. Response: Caddy encrypts the response and sends it back. The browser renders the page, and your JS then makes more /api calls, each going through steps 2–7 again.

🧠 The one idea to remember

A "server" is just a computer that's always on and has a public IP address. Everything in this guide is either (a) making sure requests can reach that computer, or (b) making sure the right program on it answers.

Permissions in 60 seconds

ls -l shows something like -rw-r--r-- 1 deploy deploy 512 .env. The three groups of rwx are what the owner, the group, and everyone else can do: read, write, execute. As numbers, r=4, w=2, x=1:

  • chmod 600 file: only the owner can read and write it (secrets, keys)
  • chmod 644 file: owner writes, everyone reads (normal files)
  • chmod 755 dir or chmod +x script.sh: executable / folder anyone can enter
  • sudo chown deploy:deploy file: change who owns it

Survive dropped connections with tmux

Part 1

Hosting on your own server

We'll set up one Ubuntu server by hand, from nothing to a live HTTPS site with automatic deploys.

1

Get a server

Goal: a fresh Ubuntu machine on the internet with a public IP address.

Best value

Hetzner Cloud

~€4/mo for 2 vCPU / 4 GB. Simple, fast, EU & US regions.

Beginner friendly

DigitalOcean / Vultr

~$6/mo. Excellent tutorials and a clean dashboard.

AWS, simplified

AWS Lightsail

$5/mo, fixed price. A good way into AWS without the complexity.

Full AWS

AWS EC2

When creating the server, choose:

  • Image / OS: Ubuntu 24.04 LTS
  • Size: 1–2 GB RAM is enough to start (2 GB makes npm run build more comfortable)
  • Region: close to your users
  • Authentication: SSH key (not a password)

Create an SSH key (if you don't have one)

Run this on your own computer, not on the server:

your computer
ssh-keygen -t ed25519 -C "my-laptop"
# press Enter to accept the default location; set a passphrase if you like

cat ~/.ssh/id_ed25519.pub
# copy this whole line and paste it into the provider's "SSH key" field
ℹ️ Public vs private key

id_ed25519.pub is the public key, and it's safe to give to servers. id_ed25519 (no .pub) is the private key. Never share it or commit it to a repo.

When the server is created, write down its public IPv4 address. That's your YOUR_SERVER_IP.

Choosing a size: a rough guide

RAMGood for
1 GBA small API + static frontend. Building on the server needs swap (step 2.6).
2 GBAPI + Postgres + builds on the server. The best starting point.
4 GBSeveral apps, Docker, Redis, background workers, or a Next.js SSR app.
8 GB+Heavy traffic, big databases, or many projects. You can resize later.

x86 or ARM?

Many providers offer cheaper ARM servers (Hetzner CAX, AWS Graviton t4g). Node, Python, Go, Postgres and most Docker images run fine on ARM. Pick x86 if you depend on an unusual native library or a Docker image that is only published for amd64.

Extra options worth turning on

  • Backups / snapshots (~20% extra): the provider takes a copy of the whole disk. It doesn't replace database backups, but it's a cheap safety net.
  • IPv6: free on most providers. Leave it on.
  • A firewall in the provider dashboard (Hetzner Firewall, DO Cloud Firewall, AWS Security Group): allow 22, 80 and 443. It blocks traffic before it even reaches your server.
✅ Check

The dashboard shows the server as Running, and you have its IPv4 address written down.

2

Connect & secure it

Goal: log in, create a non-root user, turn on a firewall, and disable password logins.

2.1 Log in for the first time

your computer
ssh root@YOUR_SERVER_IP
# On AWS EC2 Ubuntu the user is "ubuntu", not root:
# ssh -i ~/Downloads/my-key.pem ubuntu@YOUR_SERVER_IP

2.2 Update everything

server
apt update && apt upgrade -y
apt install -y unattended-upgrades   # auto-install security patches

2.3 Create a normal user

Running everything as root is risky, because one mistake or one hacked app can take over the whole machine. Make a user called deploy:

server (as root)
adduser deploy                      # set a password; skip the other questions
usermod -aG sudo deploy             # allow it to use sudo
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy   # copy your SSH key to it

2.4 Turn on the firewall

server
ufw allow OpenSSH     # port 22 — DO THIS FIRST or you'll lock yourself out
ufw allow 80          # HTTP
ufw allow 443         # HTTPS
ufw enable
ufw status
⚠️ On AWS EC2 / Lightsail

AWS also has its own firewall outside the server, called the Security Group on EC2 and the Networking tab on Lightsail. Allow inbound TCP 22 (ideally only from your IP), 80 and 443. You need both that firewall and ufw to allow traffic.

2.5 Disable password & root login

Leave your current terminal open. Open a new terminal and make sure this works:

your computer (new terminal)
ssh deploy@YOUR_SERVER_IP
sudo whoami     # should print "root"

If it works, edit the SSH config:

On Ubuntu 24.04, the main sshd_config loads files from /etc/ssh/sshd_config.d/ first, and the first value sshd reads for a setting is the one it uses. Cloud images often include 50-cloud-init.conf with PasswordAuthentication yes, which would quietly win over anything you put in the main file. So put your settings in a drop-in file whose name sorts first:

server
sudo tee /etc/ssh/sshd_config.d/00-hardening.conf > /dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
EOF

sudo sshd -t                 # test the config: no output = OK
sudo systemctl restart ssh

# confirm the settings actually in effect:
sudo sshd -T | grep -Ei 'passwordauthentication|permitrootlogin'
# → passwordauthentication no
# → permitrootlogin no

Then open one more new terminal and check that ssh deploy@YOUR_SERVER_IP still works. From here on, always log in as deploy.

🧠 Why this matters

A new server with a public IP gets automated login attempts within minutes. Bots try root / admin with thousands of common passwords. With password logins turned off, those attempts can't succeed.

🚨 Locked out?

Every provider has a web console or "recovery console" in its dashboard that lets you log in without SSH. Use it to fix sshd_config or ufw.

2.6 (Recommended) Add swap memory

Small servers can run out of RAM during npm install or npm run build. Swap gives them some extra (slow) memory to fall back on:

server
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h      # you should now see 2G of swap

2.7 Shortcut: an SSH config entry

On your computer, add this to ~/.ssh/config so you can just type ssh myapp:

~/.ssh/config (your computer)
Host myapp
    HostName YOUR_SERVER_IP
    User deploy

2.8 Block repeated login attempts with fail2ban

fail2ban watches the SSH logs and temporarily bans IPs that fail too often. On Ubuntu, SSH protection is enabled as soon as you install it:

server
sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd        # shows the number of currently banned IPs

2.9 Small quality-of-life settings

server
sudo hostnamectl set-hostname myapp-prod   # a name you'll recognise in the prompt
sudo timedatectl set-timezone UTC          # keep servers on UTC; convert in the app
sudo apt install -y htop ncdu tmux curl unzip
✅ Check

ssh myapp logs you in as deploy without asking for a password. ssh root@YOUR_SERVER_IP is refused. sudo ufw status lists only OpenSSH, 80 and 443.

Point your domain at the server

Goal: make myapp.com resolve to your server's IP.

Go to wherever your domain's DNS is managed (your registrar, or Cloudflare, which is free and has a very good dashboard) and add:

TypeNameValueNotes
A@YOUR_SERVER_IPthe bare domain, myapp.com
AwwwYOUR_SERVER_IPwww.myapp.com

Check that it worked (it can take anywhere from a minute to an hour):

your computer
dig +short myapp.com      # or: nslookup myapp.com
# should print YOUR_SERVER_IP
⚠️ Using Cloudflare DNS?

For now, set the records to "DNS only" (grey cloud). That way your server can get its own HTTPS certificate in step 7 without problems. You can switch to the orange cloud (proxied) later, but if you do, set SSL/TLS mode to Full (strict). See Proxying your VPS.

DNS record types you'll use

AAAAan IPv6 addressmyapp.com → 2001:db8::1 (add it if your server has IPv6)

TTL and "propagation"

Each record has a TTL (time to live): how many seconds resolvers may cache the answer. If the TTL is 3600 and you change the IP, some people will still get the old IP for up to an hour. Tip: lower the TTL to 300 (5 min) a day before you plan to move servers, then raise it again afterwards.

Subdomains for more services

You can add as many as you like, all pointing at the same server: api.myapp.com, staging.myapp.com, status.myapp.com. Caddy will route each one to the right place (step 12). A wildcard record * → IP covers all of them at once.

✅ Check

dig +short myapp.com @1.1.1.1 and dig +short www.myapp.com @8.8.8.8 both print your server IP. (Asking public resolvers directly avoids stale answers cached on your own machine.)

4.5 Test it by hand

server

curl http://127.0.0.1:3000/api/health

⚠️ Common mistakes here

• npm ci fails with "missing package-lock.json": commit your lockfile. It makes sure the server installs exactly the versions you tested.
• The build gets Killed: out of memory. Add swap (step 2.6).
• EADDRINUSE: something is already on port 3000. Find it with sudo ss -tlnp | grep 3000.
• Works locally, crashes on the server: usually a missing environment variable. Compare your local .env keys with the server's.

💡 Listen on localhost

Set your app to listen on 127.0.0.1 (e.g. app.listen(3000, '127.0.0.1')). Then it can only be reached through the reverse proxy, not directly from the internet. (One exception: inside Docker it has to be 0.0.0.0. See step 10.)

The unit file, line by line

LineMeaning

User=deployRun as the unprivileged user, never root.

6.4 How caching works for a built frontend

Vite gives built files a content hash in their names, like assets/index-4f8a2c.js. When the code changes, the name changes too. That means:

  • /assets/* can be cached forever: new code gets a new file name.
  • index.html must never be cached for long, because it's what points to the newest asset names. If browsers cache it, users get the old site after a deploy.

Reverse proxy & HTTPS

Goal: https://myapp.com serves the frontend, and /api goes to the backend, with a valid certificate.

The reverse proxy is the only program that faces the public internet. It handles HTTPS, serves static files, and forwards API requests to your backend. Pick one:

Caddy gets and renews HTTPS certificates automatically and needs very little config.

server
sudo apt install -y caddy
sudo nano /etc/caddy/Caddyfile      # replace everything with the config below
/etc/caddy/Caddyfile
myapp.com, www.myapp.com {
    encode gzip zstd

    # API → backend
    handle /api/* {
        reverse_proxy 127.0.0.1:3000
    }

    # Everything else → frontend files
    handle {
        root * /var/www/myapp
        try_files {path} /index.html     # makes client-side routing work on refresh
        file_server
    }

    # Cache hashed assets for a long time
    @assets path /assets/*
    header @assets Cache-Control "public, max-age=31536000, immutable"
}
server

journalctl -u caddy -f                          # watch it obtain the certificate

The Caddyfile, explained

DirectiveWhat it does
myapp.com, www.myapp.com {Which domains this block handles. Caddy gets a certificate for each one and redirects HTTP to HTTPS.
encode gzip zstdCompresses responses so pages load faster.
handle /api/* { … }Requests whose path starts with /api/. The path is passed on unchanged, so your backend sees /api/hello.
handle_path /api/* { … }(Alternative) removes the /api prefix, so the backend sees /hello. Use it if your routes don't start with /api.
reverse_proxy 127.0.0.1:3000Forwards the request and adds X-Forwarded-For/-Proto headers. WebSockets work automatically.
try_files {path} /index.htmlServes the file if it exists, otherwise index.html, so React Router or Vue Router can handle the URL.
file_serverActually sends the files.

Migrations

9.4 Better: build in CI, then upload

The simple script above builds on the server. That uses the server's RAM, and if the build breaks halfway, your site may be left half-updated. A sturdier approach is to build and test on GitHub's machines and only upload the result:

.github/workflows/deploy.yml (build-in-CI version)
name: Build & Deploy
on:
  push:
    branches: [main]

concurrency: production          # never run two deploys at once

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - name: Build frontend
        working-directory: frontend
        run: npm ci && npm run build

      - name: Build & test backend
        working-directory: backend
        run: npm ci && npm test --if-present && npm run build

      - name: Set up SSH
        run: |
          mkdir -p ~/.ssh
          echo "${{ secrets.SSH_PRIVATE_KEY }}" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          ssh-keyscan -H ${{ secrets.SERVER_HOST }} >> ~/.ssh/known_hosts

      - name: Upload & restart
        env:
          HOST: deploy@${{ secrets.SERVER_HOST }}
        run: |
          rsync -az --delete frontend/dist/ $HOST:/var/www/myapp/
          rsync -az --delete --exclude node_modules --exclude .env backend/ $HOST:~/app/backend/
          ssh $HOST 'cd ~/app/backend && npm ci --omit=dev && sudo systemctl restart myapp'
          ssh $HOST 'sleep 2 && curl -fsS http://127.0.0.1:3000/api/health'

--exclude .env also stops --delete from removing the server's .env, because rsync leaves excluded files alone.

9.5 Rollbacks: keep old releases around

When a deploy breaks production, you want to get back to the old version in seconds. A common pattern is to put every deploy in its own folder and point a current symlink at the live one:

~/releases/ ├── 20261117-1402/ ├── 20261117-1630/ ├── 20261118-0915/ ← newest └── current → 20261118-0915 (symlink)
~/deploy-release.sh
#!/bin/bash
set -euo pipefail
REPO=git@github.com:you/your-app.git
BASE=~/releases
REL=$BASE/$(date +%Y%m%d-%H%M)

git clone --depth 1 "$REPO" "$REL"
ln -s ~/shared/.env "$REL/backend/.env"         # keep .env outside releases, in ~/shared

(cd "$REL/backend"  && npm ci && npm run build)
(cd "$REL/frontend" && npm ci && npm run build)

# switch over only after everything built successfully
ln -sfn "$REL" "$BASE/current"
rsync -a --delete "$REL/frontend/dist/" /var/www/myapp/
sudo systemctl restart myapp

# keep the 5 newest releases
ls -1dt $BASE/2* | tail -n +6 | xargs -r rm -rf
echo "✅ Live: $REL"
~/rollback.sh
#!/bin/bash
set -euo pipefail
BASE=~/releases
PREV=$(ls -1dt $BASE/2* | sed -n 2p)            # second-newest release
ln -sfn "$PREV" "$BASE/current"
rsync -a --delete "$PREV/frontend/dist/" /var/www/myapp/
sudo systemctl restart myapp
echo "↩️  Rolled back to $PREV"

For this to work, point your systemd unit at the symlink: WorkingDirectory=/home/deploy/releases/current/backend. Move your .env to ~/shared/.env and set EnvironmentFile to that path. (Database migrations aren't undone by a rollback, so write migrations that the previous version of the code can still work with.)

ℹ️ Zero-downtime deploys

Restarting the service means a second or two where requests fail. To avoid that, run two copies of the app (say on ports 3000 and 3001) with reverse_proxy 127.0.0.1:3000 127.0.0.1:3001 plus lb_try_duration 5s, and restart them one at a time. Caddy sends traffic to whichever one is up. Docker setups and platforms like ECS do this kind of rolling update for you.

Frontend on S3 + CloudFront

S3 stores the files and CloudFront serves them from hundreds of locations worldwide. It costs pennies, never goes down, and needs no server.

  1. S3: create a bucket (e.g. myapp-frontend). Keep "Block all public access" on.
  2. ACM: switch the region to us-east-1 (CloudFront requires certificates from there). Request a public certificate for myapp.com and www.myapp.com, validate it via DNS, and wait until it shows "Issued".
  3. CloudFront: create a distribution:
    • Origin: your S3 bucket, with Origin Access Control (OAC). Let it update the bucket policy for you.
    • Viewer protocol: Redirect HTTP to HTTPS
    • Default root object: index.html
    • Alternate domain names: myapp.com, www.myapp.com, plus the ACM certificate
  4. SPA routing: Error pages → create custom responses for 403 and 404 → response page /index.html, code 200.
  5. DNS: point your domain to the CloudFront domain (dxxxx.cloudfront.net): an Alias A record in Route 53, or a CNAME elsewhere (Cloudflare can flatten one at the bare domain).

Deploying (install the AWS CLI and run aws configure first):

💡 Connecting the API

Option 1: host the API on api.myapp.com (an EC2 instance running Caddy) and enable CORS for https://myapp.com. Option 2 (no CORS): add the API server as a second origin in CloudFront with a behavior for /api/* and caching disabled.

Detailed: CloudFront behavior for /api/* (option 2)

  1. CloudFront → your distribution → Origins → Create origin → domain: api.myapp.com (your EC2 instance with Caddy and HTTPS), protocol HTTPS only.
  2. Behaviors → Create behavior → path pattern /api/* → that origin.
  3. Allowed methods: GET, HEAD, OPTIONS, PUT, POST, PATCH, DELETE.
  4. Cache policy: CachingDisabled. Origin request policy: AllViewerExceptHostHeader (passes cookies, query strings and headers through).

Your frontend at https://myapp.com can now call /api/... directly. One domain, no CORS.

Hosting on Cloudflare

Cloudflare runs on a huge edge network and has a very generous free tier. It's excellent for frontends. For backends there are two approaches: write your backend specifically for Workers, or keep it on your VPS and put Cloudflare in front of it.

  1. Cloudflare dashboard → Workers & Pages → Create → Pages → Connect to Git.
  2. Pick your repo. Set the root directory (e.g. frontend), build command npm run build and output directory dist.
  3. Add build-time environment variables, e.g. VITE_API_URL=https://api.myapp.com.

ℹ️ Pages vs Workers static assets

Cloudflare now also lets a Worker serve your static frontend (the "static assets" feature), so the frontend and API can live in one Worker project. Cloudflare is steering new projects towards that, but Pages is still supported and is the simplest way to start. The concepts on this page apply to both.

Pages frontend + API on your VPS (CORS & cookies)

With the frontend on myapp.com (Pages) and the API on api.myapp.com (your VPS, using the Caddy subdomain block from step 7), the browser treats them as different origins. Your API has to explicitly allow requests from the frontend's origin:

backend: npm install cors
import cors from "cors";

app.use(cors({
  origin: ["https://myapp.com", "https://www.myapp.com"],
  credentials: true,          // only if you use cookies
}));
frontend
const API = import.meta.env.VITE_API_URL;          // "https://api.myapp.com" in Pages env vars
const res = await fetch(`${API}/api/me`, { credentials: "include" });

Cookies across subdomains

myapp.com and api.myapp.com are same-site (same registrable domain), so cookies work with SameSite=Lax. Set them like this:

backend
res.cookie("session", token, {
  httpOnly: true,       // JS can't read it (XSS protection)
  secure: true,         // HTTPS only
  sameSite: "lax",
  domain: ".myapp.com",  // shared by myapp.com and api.myapp.com
  maxAge: 7 * 24 * 3600 * 1000,
});
⚠️ Don't use the *.pages.dev URL with cookies

myapp.pages.dev and api.myapp.com are different sites, and browsers increasingly block third-party cookies. Always use your custom domain for the frontend.

Things that work differently on Workers

  • There's no filesystem and no long-running process. Each request runs briefly, and in-memory variables don't persist between requests.
  • Environment variables and secrets come from c.env, not process.env (unless you enable Node compatibility).
  • Many npm packages work, especially with compatibility_flags = ["nodejs_compat"]. Native modules (e.g. bcrypt, sharp) don't. Use alternatives like bcryptjs or the Web Crypto API.
  • CPU time per request is limited (generous for normal API work; not suited to video encoding).

Putting Cloudflare in front of your VPS (orange cloud)

When you switch a DNS record to Proxied, visitors connect to Cloudflare, and Cloudflare connects to your server. You get a CDN for static files, DDoS protection, and your server's real IP is hidden.

  1. Make sure the site already works with HTTPS on the grey cloud (Caddy has its certificate).
  2. SSL/TLS → Overview → mode Full (strict). Flexible causes redirect loops with Caddy; Full without strict doesn't verify your certificate.
  3. Switch the A records to the orange cloud.
  4. SSL/TLS → Edge Certificates → turn on Always Use HTTPS.
  5. Caching → Cache Rules: add a rule to bypass cache for URI Path starts with /api/, so API responses never get cached.

Go-live checklist

Before you share the link with real users:

  • NODE_ENV=production (or the equivalent) is set, and debug mode is off (DEBUG=False in Django)
  • Error responses don't show stack traces to users
  • All secrets are real, random and different from development
  • CORS only allows your own domain(s), never * together with credentials
  • Cookies are httpOnly, secure and sameSite
  • Login and signup routes have rate limiting (e.g. express-rate-limit)
  • File uploads have a size limit, and the file type is checked
  • HTTPS works for every domain; HTTP redirects to HTTPS; SSL Labs grade A
  • Refreshing deep links works (SPA fallback)
  • A custom 404 page exists
  • Tested on a phone, over mobile data (not your Wi-Fi)
  • Backups are running, and you've done a restore drill
  • Uptime monitoring and error tracking send alerts somewhere you'll actually see them
  • You've written down how to deploy, roll back, and restore (future you will be glad)

💡 How to debug, in general

Follow the request from the inside out. Does the backend respond to curl 127.0.0.1:3000 on the server? Does the proxy respond to curl -I http://localhost? Does DNS resolve? Is the firewall open? The first step that fails is where the problem is.

Security checklist

  • Log in with SSH keys only; password and root login disabled
  • Firewall allows only 22, 80, 443 (ufw and cloud firewall)
  • unattended-upgrades installed for automatic security patches
  • App runs as a non-root user, listening on 127.0.0.1
  • Database not reachable from the internet
  • .env is chmod 600 and in .gitignore
  • HTTPS everywhere; HTTP redirects to HTTPS
  • Nightly backups, copied off the server, and a restore tested
  • Cloud billing alert set (AWS Budgets)
  • MFA on your cloud, DNS registrar and GitHub accounts
  • Optional: fail2ban to block repeated SSH login attempts (sudo apt install fail2ban)
  • Optional: uptime monitoring (UptimeRobot, Better Stack, or Uptime Kuma self-hosted)

FAQ

How much traffic can a $5 server handle?

More than you'd expect. Caddy can serve static files to thousands of visitors per second. A typical Node or Python API on 1–2 vCPUs can handle hundreds of simple requests per second. The usual bottleneck is slow database queries, not the server itself. Most side projects never come close to outgrowing a single VPS. When you do, the first step is simply resizing it to a bigger plan.

Is self-hosting secure enough?

If you follow step 2 and the security checklist, your server is better protected than most. The biggest real-world risks are, in order: leaked secrets in Git, unpatched software, weak or reused passwords on your accounts, and bugs in your own app (SQL injection, missing auth checks). Hosting it yourself doesn't make app-level bugs any better or worse.

What happens if the server dies?

With backups set up, you create a new server, run through steps 2–9 again (or docker compose up if you did step 10), restore the latest database dump, and update DNS. Writing that process down, or scripting it, turns a disaster into an hour of work. Provider snapshots make it even faster.

Can I host on a computer at home?

Yes. Use Cloudflare Tunnel so you don't need to open router ports or have a static IP. Downsides: power cuts, home internet uptime, your ISP's terms of service, and the machine being in your house. It's great for learning and personal tools. Use a VPS for anything people depend on.

Should I run my own email server?

No. Getting email delivered to inboxes (not spam) is a full-time job. For app emails (password resets, notifications) use a service like Resend, Postmark, Amazon SES or Mailgun. They give you DNS records (SPF/DKIM) to add to your domain.

Where do uploaded files (avatars, images) go?

Avoid storing them on the server's disk: it fills up, isn't backed up by default, and doesn't work once you have more than one server. Use object storage such as Cloudflare R2 or AWS S3, ideally with "presigned URLs" so the browser uploads directly to the bucket.

Docker or no Docker?

Learn without it first (steps 1–9) so you understand what's going on. Then move to Docker: it makes servers reproducible, makes moving providers easy, and it's what ECS, Fly.io, Cloud Run and Kubernetes all expect. For a single small app, either is fine.

Do I need Kubernetes?

Almost certainly not. Kubernetes is for organisations running dozens of services across many machines. A VPS with Docker Compose, or ECS, covers the vast majority of apps.

How do I move to a different provider later?

Set up the new server (Docker makes this quick), copy the latest database dump and restore it, test using the new IP, then lower the DNS TTL, briefly stop writes to the old app, take a final dump, restore it on the new server, and switch DNS over. Keep the old server running for a few days until you're sure.

Learning roadmap

  1. Week 1: Deploy the sample app through steps 1–8 by hand. Break things on purpose (stop the backend, mistype the Caddyfile, point DNS at the wrong IP) and fix them using Troubleshooting.
  2. Week 2: Deploy script, then GitHub Actions (step 9). Set up backups and do the restore drill. Add monitoring (step 11).
  3. Week 3: Move the stack to Docker Compose (step 10). Delete the server and rebuild it from scratch to prove you can. Add staging (step 12).
  4. Week 4: Move the frontend to Cloudflare Pages or S3 + CloudFront. Try a Worker.
  5. Later: RDS, ECS Fargate, Terraform, monitoring (Prometheus/Grafana), log aggregation, zero-downtime deploys.
